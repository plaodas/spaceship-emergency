# 故障カードの設計規則

100件の故障カードと、約24件の結合ノートを作るための規則です。カードは一つの故障モードだけを述べます。結合ノートは部品の接続だけを述べます。乗員症状の結論は、どちらの文書にも書きません。

関連: [技術体系](01-technology.md) / [症状50件](03-symptom-queries.md) / [デモ診断](05-demo-diagnosis.md)

## 語彙

整備文書は技術語で書く。次の乗員語は、カード本文、カード名、結合ノートに入れません。

| 乗員語 | 文書側の言い換え |
| --- | --- |
| 燃費 | 反物質の使用量、反物質消費 |
| ワープ | 超光速の航法、通常空間へ戻った直後、ジャンプ復帰 |
| エンジンルーム | 対消滅室周辺 |
| 警告灯 | 警報 |
| 右側 | 右舷 |
| 左側 | 左舷 |

言い換えは、埋め込みモデルが寄せられる表現にする。造語だけの対応（本文で一度も説明しない「ワープ＝褶曲」など）には頼らない。時間窓を書くときは「超光速の航法を終えて通常空間へ戻ったあと、90秒から180秒」とする。消費を書くときは「同じ加速度に対して反物質の使用量が増える」とする。

## 故障カード

IDは `FLT-001` から `FLT-100`。1カード1文書で、検索時に分割しない。

### 公開フィールド

| フィールド | 規則 |
| --- | --- |
| `id` | `FLT-001`〜`FLT-100` |
| `name` | 部位＋故障モード。症状の要約にしない。例: 「右舷暗黒熱弁の熱固着」 |
| `symptoms` | 整備員が観測する事実。80〜220字。乗員の口語で結論を書かない |
| `cause` | そのカードの範囲の機構だけ。下流の乗員症状まで書かない |
| `severity` | 1様子見、2次寄港、3継続監視、4系統制限、5航行中止 |
| `systems` | 主系統1つ。[技術体系](01-technology.md)の系統ID |
| `derived` | この故障が前提を作る下流カードID。因果の向きは原因から結果 |

### 検索用フィールド

| フィールド | 規則 |
| --- | --- |
| `components` | 部品IDを1〜3個 |
| `triggers` | 下記の列挙から1個以上 |
| `role` | `local` / `bridge` / `confounder` / `sensor_lie` |
| `confusers` | 表面症状が似るカードID |
| `discriminators` | このカードが真なら、報告に加えて出るはずの観測。棄却に使う |

`triggers` の値:

- `steady` — 条件を持たず続く
- `after_jump` — 通常空間へ戻ったあと90〜180秒
- `during_jump` — 折畳みの最中
- `during_burn` — 対消滅を吹かしているあいだ
- `high_power` — 高推力、または長時間の高負荷
- `shield_on` — シールド展開中
- `maneuver` — 旋回などの姿勢変更
- `comms_active` — 量子通信の使用中
- `after_heat_pulse` — 短時間の大きな熱入力のあと

`after_heat_pulse` は、ブリッジカードがジャンプの時間窓を自分の属性として持たないために置く。右舷弁の固着トリガは「大熱入力のあと」であり、その熱入力がジャンプ残熱だと結ぶのは派生辺の役目である。`FLT-044` の `triggers` に `after_jump` を入れない。

### 配分

系統ごとの枚数は [技術体系](01-technology.md) に従う。役割は次の枚数にする。

- `local` 55 — 単一系統、一つの症状族
- `bridge` 20 — 共有部品。下流カードの前提を作るが、下流の乗員症状は書かない
- `confounder` 15 — あるブリッジクラスタの表面症状に似て、識別観測が違う
- `sensor_lie` 10 — 計器の表示が実測と一致しない

役割の合計は100である。

### グラフ

- 完成コーパスでは、全カードが `derived` を1〜3件持つ。孤立ノードを禁止する。平均次数の目安は2.5。
- 自己参照を禁止する。参照先は存在するカードIDだけ。
- 因果は原因から結果へ向ける。Retriever は双方向に1ホップだけ辿る。
- デモ用に本文を先に固定するカードのうち、接続経路の端に来るものは、100件を揃えるときに下流を1件足す。その下流は [検索仕様](04-retrieval.md) の経路優先で、プロンプトから外してよい。

### 書いてよいこと、書いてはいけないこと

- 1枚のカードは、一つの故障モードだけを述べる。
- 1枚のカードに「ジャンプ復帰の時間窓」と「反物質消費の増加」を両方書かない。
- カード名を、乗員クエリの言い換えにしない。
- デモクエリ「ワープ直後だけ右側が熱い。燃費も悪化した」の二つの症状を、1枚にパッケージしない。
- 交絡カードは、熱と消費のように二つの観測を持ってよい。その場合は、時間窓か付随症状（照明、通信、対気速度、牽引）で本命と分かれるように `discriminators` を書く。
- `discriminators` は、そのカード単体が真であるときに追加で見える観測を書く。複合故障の端にいるカードへ「消費は増えない」と書かない。複合時に下流カードが消費を説明できなくなる。

## 結合ノート

別コーパス。IDは `CPL-01` から `CPL-24`。1ノート1文書。ベクトル検索の種にはせず、展開後の部品集合から引く。

| フィールド | 規則 |
| --- | --- |
| `id` | `CPL-01`〜`CPL-24` |
| `name` | 接続の名前 |
| `links` | 接続に含まれる部品ID。2〜4個 |
| `text` | 部品がどうつながるかだけ。80〜220字 |

結合ノートに乗員症状の結論を書かない。「弁を共有している」まで書く。「だから右が熱く、燃費が落ちる」は書かない。乗員語のデニーリストも適用する。

## 生成手順

1. 結合ノート24件と、`bridge` 20件を、この規則に沿って書く。`FLT-044` と `CPL-03` は予約本文を使う。
2. 残り80件をテンプレートから生成する。
3. 下のバリデータで落とす。落ちたカードは書き直す。新しい物理で通そうとしない。

## バリデータ

- 必須フィールドがある。`severity` は1〜5。`triggers` と部品IDと系統IDは列挙の中だけ。
- `symptoms` と結合ノート `text` は80〜220字。
- `derived` の参照先が存在し、自己参照がない。完成時は全カードが1件以上持つ。
- 孤立ノードがない。
- 乗員語 `燃費` `ワープ` `エンジンルーム` `警告灯` `右側` `左側` が、カードと結合ノートに無い。
- `FLT-044.triggers` に `after_jump` が無い。
- 1枚のカード本文が、ジャンプ復帰の時間窓と反物質消費の増加を同時に含まない。
- [症状50件](03-symptom-queries.md) の `compose` それぞれについて、判別に必要な事実が1文書に揃っていない。デモの4件（Q01、Q02、Q16、Q17）では、時間窓・右舷外板温度・反物質使用量の増加・弁の合流が、同一文書に共存しないこと。
